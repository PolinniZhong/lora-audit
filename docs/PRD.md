# lora-audit 产品需求文档（PRD）v0.1

> **受众**：想知道"这东西解决什么问题、给谁用、为什么长这样、不做什么"的人。
> **本文回答"要什么"**；怎么做见 [设计文档](DESIGN.md)，怎么用见 [README](../README.md)，改了什么见 [CHANGELOG](../CHANGELOG.md)。
> **依据**：一份完整的赛道与差异化调研（含逐家 star / 许可 / 最近提交的实测数据，均为 2026-09-20）。**会过期的数据留在调研侧，本文只保留结论**——star 数几周就过期，产品判断不该跟着烂。

---

## 0. 一页纸

| 项 | 结论 |
|---|---|
| **一句话定义** | 给已有的 LoRA 训练文件夹做一次**只读审计**：不用起服务、不用改你的目录结构，产出一个人能双击打开的报告。 |
| **目标用户** | 个人 / 小团队里**自己训 LoRA** 的人：手上有一个 `dataset/` 文件夹，几十到几百张图，以及一堆同名 `.txt`。 |
| **核心洞察** | 训练引擎（写）、模型管理器（分发）、caption 编辑器（写）都有人做；**"这批图到底长什么样、缺没缺 caption、trigger 有没有写歪"的只读视图是零**。 |
| **MVP 边界** | **只做**：扫一个已有文件夹 → 出只读报告。**不做**：训练、服务、数据库、桌面 App、协作、权限、语义搜索、视频音频。 |
| **成功判据** | 不是 star 数。是**用户第一次跑完，能指出至少一个他原先不知道的问题**。 |

## 1. 问题

### 1.1 谁在痛

自己训角色 LoRA 的人。他们的工作流长这样：攒图 → 打标 → 扔进 kohya / ai-toolkit → 训 → 效果不对 → **回头猜是不是数据的问题**。

### 1.2 痛在哪（三个具体场景，都是真的）

1. **"应该都打了吧"**。几十张图 + 几十个 `.txt`，文件名长得都差不多，没人会逐张核对。缺一张、空一个文件、trigger 在一张上写错，**肉眼看不出来**，但训练时会实实在在吃掉效果。
2. **变量没写进 caption**。两张不同的图 caption 一字不差（复制粘贴留下的），等于告诉模型"这两张一样"。这类问题**只有把 caption 并排看才发现**。
3. **效果不对时无从归因**。数据集是两个月前攒的、中间改过几轮，**已经没人知道当前这批图是怎么来的**。

### 1.3 为什么现在

- 训练端已经平民化（kohya_ss / ai-toolkit 都是万人级项目），**用的人多了，"数据里到底有什么"才成为问题**；
- 但生态的注意力全在"怎么训得更好"（参数、底模、采样器），**数据侧的工具停留在"看图改标签"的单机小工具**；
- 现有方案要么是**必须起服务的企业级 DAM**（对个人过重），要么是**通用照片相册**（停在"看图"层，没有生产语义）。

## 2. 竞争与空白

### 2.1 五类相邻方案，以及它们为什么都不解决这个问题

| 类别 | 它们在做 | 为什么不是竞品 |
|---|---|---|
| 通用开源 DAM / MAM | ingestion → 索引 → 检索 / 发布 | **状态词全是消费态**（已备份 / 收藏 / 归档 / 已发布），没有一家把"这张资产过到第几道工序"当一等概念；且都要起服务 + 数据库 |
| SD / ComfyUI / LoRA 训练生态 | 出图、训练、装节点、下模型 | 训练引擎只认"图 + 同名 txt"，模型管理器只认 `.safetensors`。**写侧有人做，读侧为零** |
| 训练数据集可视化库 | 训练前在几百张标注里挑脏数据 | 面向 ML 工程师的 Python 库 / notebook 工作流，**不是创作者的资产视图**，也不解决"这套数据是怎么来的" |
| 静态 / 离线画廊 | 扫目录 → 生成无后端静态相册 | 路线对，但**停在"通用照片相册"层**，没有 AIGC 生产语义 |
| Agent Skill 生态 | 角色一致性**生成**技巧（提示词方法论） | 教你怎么把图画得一致，**不是资产账房**：不跨库编目、不追踪阶段门、不产出确定性训练集 |

### 2.2 我们声称的能力，谁做了谁没做

| 能力 | 通用 DAM | 训练生态 | 静态画廊 | Agent Skill | 判定 |
|---|---|---|---|---|---|
| 跨多资产库共用契约（稳定 ID + 内容指纹反查） | ❌ | ❌ 各家约定互不兼容 | ❌ | ❌ | **真空白** |
| 阶段门 / SOP 作为可对账的工序流 | ❌ 有审批流，无工序流 | ❌ SOP 都写在博客里 | ❌ | ❌ | **真空白** |
| 训练素材的确定性产出 + 双 caption profile + 分层 val + 哈希审计 | ❌ | ❌ 自动打标只出单份 caption | ❌ | ❌ | **最硬的差异化** |
| 纯静态、离线、只读、双击即开 | ❌ 全部要起服务 + 数据库 | ❌ 都要进程 / 云端 | ✅ 走通了 | ❌ | **入场券** |

### 2.3 关键判断：把"真差异化"和"入场券"分开

这条判断决定了产品的**对外说法**：

- **真差异化**（别人做不了或没做）：训练素材的确定性产出与审计；"写侧一堆、读侧为零"的中间断档；文件夹即契约（数据先在文件夹里，工具只生成只读快照）。
- **入场券，不是卖点**：纯静态 / `file://` 双击即开。这条路已经有人走通过，它只是**让你能进来**，不是让人选你的理由。**不进产品主打语。**
- **自嗨型差异化**（别人不做只是因为不重要，或我们高估了通用性）：设计令牌 / 阴影层级 / 看图组件；"加新库零代码"这种架构收益（单个用户只有一个库，用不上）；**以及我们自己那套完整方法论（多阶段门 SOP、跨库资产契约、一个整合式浏览前端）——默认形态过重**。

**这三个分类直接决定了 MVP 边界**（§3.3）。

## 3. 产品定义

### 3.1 一句话

**给定一个已有的训练文件夹，自动生成一个只读静态报告，把"人眼看不出来的数据问题"摊开。**

### 3.2 输入与输出（"零契约"的严格定义）

| | 要求 |
|---|---|
| **输入** | 一个普通文件夹。**不要求** manifest、声明文件、配置文件、数据库、任何命名规范。已有的目录结构就是输入。 |
| **输出** | **单个自包含 HTML 文件**，双击即开，离线可用（零远程资源 / 零 ES Module / 零运行时请求）。 |
| **副作用** | **只多一个 `_lora_audit/` 目录**。不移动、不改名、不改写数据集里的任何文件。 |

零契约是**产品需求**，不是实现洁癖：相邻生态的默认假设是"先起服务、数据进数据库"，而真实用户是"**先把图糊进一个文件夹，再想办法救**"。要求对方先按我们的规范整理，方向就是反的。

### 3.3 非目标（写死，不接受"顺手做一下"）

- 训练能力（只读数据，不碰 kohya / ai-toolkit / OneTrainer）
- 本地服务 / 数据库 / 桌面 App / Docker 镜像
- 团队协作、权限控制、语义搜索、实时编辑
- 视频与音频
- 任何需要联网的功能（包括"顺手查一下这个模型"）
- 把我们自己那套完整方法论作为默认：**阶段门 SOP、跨库资产契约、整合式浏览前端一律不进 MVP**

> 理由见 §2.3——每一条都是"别人不做是因为不重要，或我们高估了它的通用性"。把它们砍掉，MVP 才只剩一件事。

## 4. 需求

### 4.1 功能需求

状态列对应已发布的 `0.1.0`。

| # | 需求 | 优先级 | 验收标准 | 状态 |
|---|---|---|---|---|
| FR-1 | 吃一个文件夹，出**单文件**报告 | P0 | 产物能被单独打开；`verify` 通过三条离线不变量 | ✅ |
| FR-2 | 检出**缺 caption** | P0 | 指到具体文件；区分"没有同名 txt"与"有 `default_caption` 兜底" | ✅ `E001`/`W004` |
| FR-3 | 检出**空 caption 文件** | P0 | 空文件比缺文件更隐蔽，必须单独报 | ✅ `W001` |
| FR-4 | 检出**逐图 caption 重复** | P0 | 给出重复组与原文片段 | ✅ `W002` |
| FR-5 | 提取**触发词**并报**不一致** | P0 | 推定主流触发词；证据不足时**不报**（≥3 张且覆盖 ≥60%） | ✅ `W003` |
| FR-6 | 检出**孤儿 caption**（有 txt 无图） | P1 | 不被"镜像 caption 目录"误伤 | ✅ `W006` |
| FR-7 | 检出**文件名 / 分辨率 / 规模 / 杂物 / 清单死链 / val 未分层** | P1 | 每条都不误报；分辨率不统一要带让步措辞 | ✅ `W005`/`W007`–`W012` |
| FR-8 | 检出**扩展名与实际格式不符** | P2 | 按文件头判定，不按扩展名 | ✅ `W013` |
| FR-9 | **每条问题都带一句「怎么办」** | P0 | 没有出口的告警不出现 | ✅ |
| FR-10 | 支持真实存在的多种布局 | P0 | kohya 平铺 / `N_名称` 重复目录 / ai-toolkit（`img/`+`default_caption.txt`）/ 双 caption profile / 按子目录分组 / 混合 | ✅ |
| FR-11 | 报告**能筛、能搜、能看大图、能复制 caption** | P1 | 真浏览器实测逐项通过 | ✅ |
| FR-12 | **机读输出**，可进 CI | P1 | `--json -` 的 stdout 是**纯 JSON**（摘要走 stderr）；`--strict` 让警告也影响退出码 | ✅ |
| FR-13 | 产物**不变量自检** | P0 | `verify` 独立检查产物（不依赖生成逻辑） | ✅ |
| FR-14 | 缩略图通道（大数据集首屏性能） | P1 | 上千张时首屏可用；需要图像库 | ❌ 未实现 |
| FR-15 | manifest 支持（可选的门进度条） | P2 | **只在用户已经有 manifest 时才启用**，不要求他写 | ❌ 未实现 |
| FR-16 | 英文界面 | P2 | 文案 i18n | ❌ 未实现（界面文案目前中文） |

### 4.2 体验需求

| # | 需求 | 理由 |
|---|---|---|
| UX-1 | **零必需依赖**，`pip install` 一次装好 | 为一个宽高读数背一个 C 扩展不划算；审计只需要读文件 + 正则 + 写 HTML |
| UX-2 | 30 秒内出第一份报告 | 不建索引、不起服务、不扫全盘 |
| UX-3 | 问题**优先于图片**出现在第一屏 | 用户是来查问题的，不是来逛相册的 |
| UX-4 | 首次运行**不需要读任何文档** | 命令就一条；报告自解释 |
| UX-5 | 告警**宁可少报也不误报** | 噪声一旦出现，用户下次就不看了 |

### 4.3 规则收录判据

新规则必须同时满足六条（R1 能一眼验证 / R2 不猜意图 / R3 有明确出口 / R4 宁可漏报不误报 / R5 不引必需依赖 / R6 不改输入），细则与**通过与不通过的具体反例**见 [CONTRIBUTING](../CONTRIBUTING.md) §2。

> 一句话：**凡是需要读图内容、需要调模型、需要"感觉一下"的规则，一律不收。**

## 5. 成功判据

**明确不用 star 数当判据。** 三个可观测的：

1. **可用性**：用户第一次跑完，能说出至少一个他原先不知道的问题。（如果做不到，这个产品就不成立——这是最核心的一条。）
2. **被引用**：有人把它接进自己的流程——CI、ComfyUI 教程里被提一句、模型发布页附一张审计截图。
3. **可复现**：issue 里给的"目录树 + caption 原文"能稳定复现同一个结果。这证明行为可预测，而不是玄学。

**预期量级**：一个**有用的小工具**（数百 star 量级），不是爆款。这是基于"这个细分真空白，但没人喊疼"（§6）得出的，不是谦虚。

## 6. 风险与反方观点（必须正视）

| # | 风险 | 应对 |
|---|---|---|
| 1 | **没人喊疼**。翻遍社区，没有爆款帖在说"我需要一个工具管我的训练资产"——痛点是真的，但被当成"我自己硬盘的事"，没上升成产品需求 | 所以**前 100 个 star 会非常难拿**；MVP 必须证明"扫一眼就能看到你自己看不到的问题"，而不是"我帮你把资产组织得很规范" |
| 2 | **社区可能真的只想要"一个文件夹 + 一张 Excel"** | 若如此，我们的价值主张就不成立。这也正是 §5 第 1 条判据存在的意义 |
| 3 | **维护者诅咒**：这个细分里活得好的都是个人维护者 | 明确定位为"验证方法论"而不是"长期维护的产品"；README 与本文都不承诺路线图 |
| 4 | **静态路线的天花板**：解决不了多人协作 / 实时编辑 / 权限 | **敢说"不解决"**，并且在文档里写死为非目标（§3.3） |
| 5 | **"加新库零代码"讲不出去**：99% 的用户只有一个库 | 不进对外说法（§2.3） |
| 6 | **自家方法论的自嗨风险最高** | 已用 MVP 边界回避：整套方法论不进 MVP；只留"文件夹即契约"这一条真正对用户有利的原则 |

## 7. 已交付 vs 未交付（`0.1.0` 诚实对照）

**已交付**：FR-1～FR-13 全部；17 条规则；4 种真实布局 + 镜像 caption 目录；单文件离线报告；`verify` + 真浏览器实测两道验证。

**未交付**：FR-14 缩略图通道、FR-15 manifest、FR-16 英文界面（触发条件见 §8）。

**验证到什么程度（这一栏必须诚实）**：
- 合成夹具覆盖 7 类已知缺陷；
- 15 个按训练器**官方约定**构造的布局夹具；
- **1 个真实第三方公开数据集**（9 张、零 caption、`.png` 实为 WebP）——就是这一跑，掉出了"按扩展名分派解析器"和"`--json` stdout 被污染"两个合成夹具发现不了的问题；
- **尚未经受"大量真实目录"的考验。**

## 8. 触发条件：什么时候该重新考虑

| 项 | 触发条件 |
|---|---|
| `--thumbs` 缩略图通道（要引入图像库） | 有用户报"上千张太慢" |
| manifest 支持（可选的门进度条） | 用户**手里已经有** manifest，而不是我们要求他去写 |
| 英文界面 | 英文用户反馈界面看不懂 |
| 多触发词 / caption 模板 | 出现真实用例 |
| 视频 / 音频 | **不做**——那是另一个工具 |

## 9. 本文与其它文档的关系

```
README.md          怎么用            （用户）
   ↓
docs/PRD.md        要什么、给谁、不做什么  ← 本文
   ↓
docs/DESIGN.md     怎么做、为什么这么做、代价是什么
   ↓
CONTRIBUTING.md    什么样的贡献会被收
CHANGELOG.md       改了什么
   ↓
调研侧（不随仓库分发）  证据：逐家实测数据、原始判断过程
```

**PRD 是决策层，调研是证据层。** 两者不重复：本文只写"决定了什么"，调研负责"凭什么这么决定"。
